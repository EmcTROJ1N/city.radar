# Оценка качества LLM-разбора

В каталоге лежит инструмент и формат данных для приёмочной оценки качества LLM:
precision опубликованных без модерации наблюдений и recall экстрактора и линкера.
Реальный размеченный набор (200–500 сообщений) готовит заказчик; инструмент работает
и без него — на синтетическом `sample.jsonl`.

Инструмент — консольный проект `backend/tests/Ingestion.LlmEval`. Он прогоняет каждое
сообщение через **тот же `MessagePipeline`, что и Worker** (`Ingestion.Pipeline`): тот же
системный промпт, те же проверки статуса, цитаты, фиксации и порога confidence. Меняется
только провайдер LLM: реальный OpenAI-совместимый (`--provider openai`) или эвристический
fake (`--provider fake`).

## Состав

| Файл | Назначение |
|---|---|
| `sample.jsonl` | Синтетический набор из 12 сообщений: вода есть/нет/ограничена, нерелевантное, неоднозначное, prompt injection, несколько фиксаций. |
| `sample.sources.json` | Конфигурация источника к примеру: статусы, фиксации, режим «по тексту», порог confidence. |
| `backend/tests/Ingestion.LlmEval` | Консольный раннер (`EvalRunner`, `EvalReport`). |
| `backend/src/Ingestion/Ingestion.LlmEval.Core` | Библиотека раннера: разбор набора, метрики, отчёт, регрессия. |

Наборы и отчёты с реальными сообщениями **не коммитятся** в репозиторий, если содержат
персональные данные: набор должен быть обезличен.

## Формат набора (`.jsonl`)

Одна строка — один случай, UTF-8. Пустые строки пропускаются. Обязательные поля:

```json
{"text":"В доме № 5 на улице Ленина нет воды с самого утра.","expected":{"relevant":true,"status":"no_water","objectCode":"center"}}
```

| Поле | Обязательно | Значение |
|---|---|---|
| `text` | да | Текст сообщения в том виде, в каком он попал бы в pipeline. Не пустой. |
| `expected.relevant` | да | `true` — сообщение о состоянии ресурса по промпту источника; `false` — нерелевантное. |
| `expected.status` | да (может быть `null`) | Код статуса **из конфигурации источника**. `null` допустим для нерелевантного или неоднозначного сообщения. |
| `expected.objectCode` | да (может быть `null`) | Код фиксации из конфигурации источника; `null`, если фиксацию по тексту определить нельзя. |
| `id` | нет | Уникальный идентификатор случая. Без него используется `case-<номер строки>`. |
| `note` | нет | Комментарий разметчика: почему такой статус, что было неоднозначно. |

Правила проверки при загрузке:

- невалидный JSON, отсутствующее поле или неверный тип — ошибка с **номером строки**;
- для `relevant: false` поля `status` и `objectCode` обязаны быть `null`;
- `status` и `objectCode` сверяются с `--sources`: опечатка в коде — ошибка набора,
  а не «модель ошиблась»;
- пустой набор — ошибка.

## Формат конфигурации источника (`--sources`)

Если `--sources` не задан, используется встроенный пример (совпадает с `sample.sources.json`).

```json
{
  "sourceId": "9f1c7d2e-4b8a-4c3d-9e5f-1a2b3c4d5e6f",
  "name": "Водоканал (пример)",
  "userPrompt": "Ищи сообщения о наличии, отсутствии или ограничении подачи воды.",
  "linkByText": true,
  "confidenceThreshold": 0.7,
  "statuses": [
    {
      "code": "no_water",
      "name": "Нет воды",
      "description": "Подача воды прекращена, воды нет.",
      "fakeKeywords": ["нет воды", "воды нет"]
    }
  ],
  "objects": [
    {
      "code": "center",
      "name": "Центральный район",
      "address": "ул. Ленина, 1–20",
      "fakeKeywords": ["центр", "ленина"]
    }
  ],
  "prefilter": { "keywords": [], "regexes": [] }
}
```

| Поле | Назначение |
|---|---|
| `sourceId` | Идентификатор источника. Необязателен; при отсутствии берётся фиксированный. Идентификаторы статусов и фиксаций выводятся из него детерминированно, поэтому отчёт воспроизводим без БД. |
| `name` | Название источника для отчёта. |
| `userPrompt` | Промпт-фильтр пользователя; его можно заменить файлом `--prompt`. |
| `linkByText` | Режим «определять фиксацию по тексту». Влияет на recall линкера. |
| `confidenceThreshold` | Порог confidence источника, 0..1. Ниже — модерация `low_confidence`. |
| `statuses[]` | Коды, названия и описания статусов; попадают в системный промпт. |
| `objects[]` | Коды, названия и адреса фиксаций; попадают в промпт в режиме «по тексту». |
| `prefilter` | Необязательный префильтр (`keywords`, `regexes`) для проверки шага 1 pipeline. |
| `fakeKeywords` | Только для `--provider fake`: подстроки, по которым эвристика выбирает статус/фиксацию. На реальный pipeline не влияют. |

Совет: для приёмочного набора берите конфигурацию **реального источника** из админки
(коды статусов, названия и адреса фиксаций, промпт, режим, порог). Иначе измеряется не тот
промпт, который работает в проде.

## Запуск

Из каталога `backend`:

```bash
# Проверка инструмента без ключа LLM (эвристический fake):
dotnet run --project tests/Ingestion.LlmEval -- \
  --dataset ../datasets/llm-eval/sample.jsonl \
  --sources ../datasets/llm-eval/sample.sources.json \
  --provider fake \
  --out ../datasets/llm-eval/report.md

# Реальная оценка:
export MAYAK_LLM_API_KEY=...          # в отчёт и логи не попадает
export MAYAK_LLM_MODEL=gpt-4o-mini
export MAYAK_LLM_BASE_URL=https://api.openai.com/v1   # необязательно
export MAYAK_LLM_PROXY=socks5://user:password@host:1080  # необязательно

dotnet run --project tests/Ingestion.LlmEval -- \
  --dataset ../datasets/llm-eval/real-2026-11.jsonl \
  --sources ../datasets/llm-eval/water-source.json \
  --provider openai \
  --out ../datasets/llm-eval/report-2026-11.md

# Регрессия относительно предыдущего прогона:
dotnet run --project tests/Ingestion.LlmEval -- \
  --dataset ../datasets/llm-eval/real-2026-11.jsonl \
  --sources ../datasets/llm-eval/water-source.json \
  --provider openai \
  --baseline ../datasets/llm-eval/report-previous.json \
  --min-precision 0.95 \
  --out ../datasets/llm-eval/report-current.md
```

Параметры:

| Параметр | По умолчанию | Значение |
|---|---|---|
| `--dataset <файл>` | обязателен | JSONL-набор. |
| `--sources <файл>` | встроенный пример | Конфигурация источника. |
| `--prompt <файл>` | из конфигурации | Заменить промпт-фильтр текстом файла. |
| `--provider openai\|fake` | `openai` | Реальная модель или эвристика. |
| `--out <файл>` | `llm-eval-report.md`/`.json` | Отчёт: по расширению `.md`/`.json`; иначе пишутся `<файл>.md` и `<файл>.json`. |
| `--baseline <отчёт.json>` | — | Включить регрессионную проверку. |
| `--min-precision <0..1>` | `0.95` | Абсолютный порог precision в регрессионном режиме. |

Ключ LLM не печатается и не записывается в отчёт: в отчёте есть только имя модели и хеш
промпта. `--provider fake` **не измеряет качество модели** — он нужен, чтобы проверить
сам инструмент, формат набора и отчёты без ключа и без расходов на API.

Коды возврата: `0` — успех; `1` — регрессия; `2` — ошибка аргументов/набора/конфигурации;
`3` — внутренняя ошибка; `130` — отмена по Ctrl+C.

## Как подготовить набор 200–500 сообщений

Набор готовит заказчик. Пока набора нет, задача оценки не блокируется: инструмент
и синтетический пример уже в репозитории.

1. **Выборка.** Возьмите 200–500 реальных сообщений из тех чатов, которые будут подключены
   как источники. Разные дни недели и часы, будни и выходные, периоды аварий и обычной работы.
   Не выбирайте только «удачные» сообщения: нужны и нерелевантные, и спорные.
2. **Обезличивание.** Удалите имена, телефоны, адреса квартир и прочие персональные данные.
   Дом и район можно оставить: они нужны для определения фиксации. Набор и отчёты с реальными
   данными не коммитьте в публичный репозиторий.
3. **Разметка.** Для каждого сообщения заполните `relevant`, `status`, `objectCode` строго
   по конфигурации источника. Размечайте по смыслу сообщения, а не по тому, что, по-вашему,
   ответит модель. Цитату не размечайте: её правильность проверяет код pipeline.
4. **Спорные случаи.** Если сообщение допускает два статуса — выберите основной и объясните
   в `note`. Если статус определить нельзя — `relevant: true`, `status: null`; такой случай
   попадёт в precision, но не в recall экстрактора. Если сообщение не о состоянии ресурса —
   `relevant: false`, оба кода `null`.
5. **Покрытие.** Ориентир: 20–30% нерелевантных сообщений, по 30–50 сообщений на каждый
   статус, отдельно сообщения с несколькими фиксациями и с попытками prompt injection.
6. **Согласование.** Два разметчика независимо размечают 20–30 случаев; расхождения
   обсуждаются и фиксируются правилом. Один человек размечает весь набор, второй выборочно
   проверяет.
7. **Версионирование.** Набор — файл с датой или версией (`real-2026-11.jsonl`). При смене
   модели или промпта прогоняйте **тот же** набор и сохраняйте JSON-отчёт как baseline.
8. **Переразметка.** Если изменился промпт источника или набор статусов, проверьте, не устарела
   ли разметка. Старые отчёты остаются историей, но сравнивать метрики с новой разметкой нельзя.

## Метрики и как их читать

Отчёт содержит Markdown для человека и JSON для CI/регрессии. В JSON есть метаданные
(`provider`, `model`, `promptHash`, `generatedAt`, `datasetSize`), метрики и результат
по каждому случаю.

### Precision опубликованных наблюдений

```
precision = верные опубликованные наблюдения / все опубликованные наблюдения
```

Единица — **наблюдение**, а не сообщение. Если режим «по тексту» выключен, одно сообщение
публикует статус на все фиксации источника; каждая публикация входит в знаменатель.
Верное наблюдение совпадает и по статусу, и по фиксации (если разметчик фиксацию указал).
Это главная метрика: она отвечает на вопрос «какая доля того, что мы показали
на карте без модератора, верна». Цель — **≥ 0,90**.

### Recall экстрактора

```
recall_экстрактора = случаи с верным предложенным статусом /
                     случаи, размеченные как релевантные и имеющие статус
```

Засчитываются и публикация без модерации, и карточка модерации, в которой предложен верный
статус. Метрика отвечает на вопрос «извлекла ли модель правильный статус», а не «попал ли
он на карту»: сообщение может уйти в модерацию из-за низкого confidence, но статус всё равно
распознан верно. Цель — **≥ 0,70**.

### Recall линкера

```
recall_линкера = случаи с верно найденной фиксацией /
                 релевантные случаи с размеченной фиксацией
```

Считается только в режиме «определять фиксацию по тексту» при нескольких фиксациях. Если
режим выключен, фиксация не определяется, а при одной фиксации выбора нет — метрика `n/a`.
Засчитывается верный `object_id` и в публикации, и в карточке модерации. Цель — **≥ 0,70**.

### Модерация по причинам

Доли от всего набора:

| Причина | Что означает |
|---|---|
| `low_confidence` | Модель уверена ниже порога источника. |
| `invalid_status` | Код статуса не из списка этого источника. |
| `object_not_found` | Фиксация не определена или не входит в список источника. |
| `invalid_response` | Невалидный JSON, отсутствие поля, цитата не подстрока. |
| `llm_error` | Сбой провайдера: сеть, прокси, HTTP-ошибка. |

В БД `llm_error` и «цитата не подстрока» хранятся как `invalid_response` (check-констрейнт
схемы), но отчёт разделяет их для диагностики.

### Матрица ошибок по статусам

Строки — ожидаемый статус (или «нерелевантно»/«без статуса»), столбцы — предложенный статус
(или «нет предложения»). По матрице видно, какие статусы модель путает: например, «нет воды»
и «ограничение подачи».

### Ошибки

В конце Markdown-отчёта — до 100 случаев, где решение не совпало с разметкой, с фрагментом
текста, ожиданием и фактом. Полный список — в JSON (`cases[].correct`).

## Регрессионный режим

`--baseline <предыдущий-report.json>` сравнивает текущий прогон с baseline и возвращает
код `1`, если:

- precision **ниже** `--min-precision` (по умолчанию `0.95`); если публикаций не было,
  precision не определена и порог считается невыполненным;
- precision упала **более чем на 2 п.п.** относительно baseline (правило из,
  даже если абсолютный порог ещё не нарушен).

Целевое значение — precision ≥ 0,90. Порог регрессии по умолчанию строже (0,95),
чтобы ловить деградацию до того, как она упрётся в приёмочный минимум; для приёмки можно
запускать с `--min-precision 0.9`. Итог сравнения попадает в Markdown-раздел «Регрессия»
и в консольный вывод.

## Ограничения

- `sample.jsonl` синтетический: он проверяет формат и инструмент, а не качество модели.
- `--provider fake` — эвристика по `fakeKeywords`, а не модель; метрики на нём не являются
  оценкой качества LLM.
- Прогон не ходит в Telegram и не использует БД: источник, статусы и фиксации задаются
  конфигурацией, а сообщения — набором.
- Один прогон — один источник. Для нескольких источников запускайте инструмент отдельно
  с разными `--sources` и наборами.
